### T003 — Elena's HTTP/origin/credential audit at T003 (code inspection only)

- `src/tactical-ui.js` sends `POST` JSON `{goal,state}` to the relative `/api/tactical-coach` URL, with no explicit `Authorization`, bearer token, or `credentials` option. The browser therefore uses its normal same-origin fetch credential behavior, but the inspected route neither authenticates nor reads cookies/session/Authorization as a privilege grant. `src/main.js` derives `state` from the browser-owned `game` object; direct HTTP clients can bypass this UI. This is a local/demo single-user Coach over client-reported state, not private per-user game storage or a verified match result.
- `vite.config.js` proxies `/api` to `http://127.0.0.1:3001` **under `server.proxy`** (development configuration; installed Vite 7 also inherits it in preview unless overridden). The browser sees the Vite development origin for the relative request; Vite forwards it to the loopback API target. `package.json` defines `dev: vite`, `build: vite build`, `preview: vite preview`, `build:server`, `dev:api`, and `start:api`. The API entrypoint listens on `127.0.0.1` port 3001 by default. No cross-origin production deployment is observed in these files. There is no explicitly declared `preview.proxy` in project config. Installed Vite 7 inherits `server.proxy` when preview-specific proxy is absent, but T008 uses a test-only inline proxy to a dynamic loopback API port rather than depending on that implicit behavior. **W08 GAP — not implemented yet:** T038 must configure and verify the explicit production preview proxy/security profile in project config.
- `server/index.ts` creates one Node HTTP server. The Tactical route checks POST, JSON media type, 4096-byte body and exact parsed request before calling `providerFactory()`; response writing sets JSON `Content-Type` and `Allow` for wrong methods. No `Access-Control-Allow-Origin` or credentialed CORS response policy is set here. CORS is not authentication, and same-origin development proxy use does not require a broad CORS grant. If frontend/API later become cross-origin, define and enforce a server-owned origin/credentials policy before provider work, then retest. Do not infer that an arbitrary cross-origin deployment is supported from this local configuration.
- **Conditional CSRF finding:** in the inspected local route, no cookie/session or other ambient credential grants privileged user access, and there is no login/private-resource model. On that observed architecture, a CSRF token mechanism is not currently applicable; this finding depends on the actual credential/origin boundary and must be reassessed if cookie authentication, privileged ambient credentials, or hosting topology changes. Cross-site request effects and public resource consumption still require server-owned admission controls; CSRF non-applicability does not waive rate/concurrency protection. No authentication is proposed merely to satisfy a test.
- W05 has per-run orchestrator budgets but no server-instance `activeRuns`, rolling `admittedRuns`, shared database/session store, or distributed limiter in the inspected API. **W08 GAP — not implemented yet:** T031–T033's server-owned maximum 2 active runs and 5 newly admitted valid runs per rolling 60 seconds, scoped to this one local process; there is no claim across processes/hosts. No browser field may set these limits or select the provider.
- `src/tactical-ui.js` parses exact response fields, clears with `replaceChildren()`, and renders summary/actions/evidence/badges through created nodes with `textContent`; status messages also use `textContent`. The inspected Tactical UI has no `innerHTML`, Markdown-to-HTML renderer, automatic linkification, `eval`, or dynamic script creation. This is an existing W05 rendering control, not a T04/T05 real-browser proof. **W08 GAP — not implemented yet:** `vite.config.js` declares no production-preview CSP or `X-Content-Type-Options`/`Referrer-Policy` headers; T038–T040 must implement/verify delivery with a real browser and controlled HTTP-200 second-origin script.

### T031–T034 — Tactical admission and event controls (current working tree, uncommitted)

The T023–T026 before-hardening checkpoint at `9799bbe7b99d49b853a35c51073a4bdb611bd958` measured **1 pass, 4 TODO**: a third held request entered the provider (peak fake activity 3); the sixth valid arrival in one window executed provider and tools; there was no production active-slot lifecycle or request security-event sink. These are before observations, not the result of the implementation below.

The current implementation creates one in-memory `createTacticalAdmission()` object per `createApiServer()` instance in `server/tactical/admission.ts`. Its default server-owned clock is monotonic `performance.now()`; tests inject a fake clock through server configuration, never an HTTP field. After the existing method, media type, 4096-byte body, JSON, exact `goal,state`, and domain validation, a synchronous `tryAdmit()` prunes timestamps older than the rolling **60,000 ms** window, checks **five newly admitted valid runs** and **two active runs**, then atomically records one timestamp and reserves one active slot. Invalid, active-rejected, and rate-rejected arrivals record no admission timestamp. Excess gets a fixed, small HTTP **429** error before provider construction, provider attempt, or tool execution. This is per server instance in one Node process, with no distributed/global guarantee or client identity policy.

Each accepted request owns one idempotent lease. The handler releases it in `finally` after orchestration success, controlled failure, timeout, abort, or socket disconnect; a later provider settlement cannot write a success response, start another application step, or release a second time. An already-issued external provider operation must honor its abort signal for physical cancellation; this local slot tracks the application run, not remote network work after an aborted attempt. Releasing the lease immediately restores active capacity but does **not** remove its rolling-window timestamp. A timestamp ages out only when the server clock reaches its 60-second boundary. The focused test inspects server-owned `activeRuns`, rolling `admittedRuns`, and `releasedRuns` through a server-side injected admission object; none of these counters is returned to the browser.

Each Tactical request gets an application-generated `crypto.randomUUID()` correlation ID. `server/tactical/security-events.ts` builds only fixed `agent.run.admitted`, `agent.run.rejected`, and `agent.run.completed` records containing `event`, server `timestamp`, generated `correlationId`, fixed `reason`/`outcome`, and completion-only observed `providerAttempts`/`executedToolCalls`. These counters are counted around actual provider/tool calls and included only when they are safe integers within the existing four-attempt/two-tool budgets; an unavailable or out-of-range count is omitted rather than invented or clipped. The injectable sink receives the fixed record directly; the default local operational sink writes one JSON line per record with `console.info`. Raw goal, state/statistics, provider output, secret, token/cookie, chain-of-thought, stack, and attacker newline/fake-event text are never event fields. Sink failure is isolated from the HTTP decision. Correlation IDs and security limits cannot be supplied by the HTTP caller.
