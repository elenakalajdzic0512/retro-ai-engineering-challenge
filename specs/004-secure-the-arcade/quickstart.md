### T031–T034 — Tactical admission and event controls (current working tree, uncommitted)

The T023–T026 before-hardening checkpoint at `9799bbe7b99d49b853a35c51073a4bdb611bd958` measured **1 pass, 4 TODO**: a third held request entered the provider (peak fake activity 3); the sixth valid arrival in one window executed provider and tools; there was no production active-slot lifecycle or request security-event sink. These are before observations, not the result of the implementation below.

The current implementation creates one in-memory `createTacticalAdmission()` object per `createApiServer()` instance in `server/tactical/admission.ts`. Its default server-owned clock is monotonic `performance.now()`; tests inject a fake clock through server configuration, never an HTTP field. After the existing method, media type, 4096-byte body, JSON, exact `goal,state`, and domain validation, a synchronous `tryAdmit()` prunes timestamps older than the rolling **60,000 ms** window, checks **five newly admitted valid runs** and **two active runs**, then atomically records one timestamp and reserves one active slot. Invalid, active-rejected, and rate-rejected arrivals record no admission timestamp. Excess gets a fixed, small HTTP **429** error before provider construction, provider attempt, or tool execution. This is per server instance in one Node process, with no distributed/global guarantee or client identity policy.

Each accepted request owns one idempotent lease. The handler releases it in `finally` after orchestration success, controlled failure, timeout, abort, or socket disconnect; a later provider settlement cannot write a success response, start another application step, or release a second time. An already-issued external provider operation must honor its abort signal for physical cancellation; this local slot tracks the application run, not remote network work after an aborted attempt. Releasing the lease immediately restores active capacity but does **not** remove its rolling-window timestamp. A timestamp ages out only when the server clock reaches its 60-second boundary. The focused test inspects server-owned `activeRuns`, rolling `admittedRuns`, and `releasedRuns` through a server-side injected admission object; none of these counters is returned to the browser.

Each Tactical request gets an application-generated `crypto.randomUUID()` correlation ID. `server/tactical/security-events.ts` builds only fixed `agent.run.admitted`, `agent.run.rejected`, and `agent.run.completed` records containing `event`, server `timestamp`, generated `correlationId`, fixed `reason`/`outcome`, and completion-only observed `providerAttempts`/`executedToolCalls`. These counters are counted around actual provider/tool calls and included only when they are safe integers within the existing four-attempt/two-tool budgets; an unavailable or out-of-range count is omitted rather than invented or clipped. The injectable sink receives the fixed record directly; the default local operational sink writes one JSON line per record with `console.info`. Raw goal, state/statistics, provider output, secret, token/cookie, chain-of-thought, stack, and attacker newline/fake-event text are never event fields. Sink failure is isolated from the HTTP decision. Correlation IDs and security limits cannot be supplied by the HTTP caller.
