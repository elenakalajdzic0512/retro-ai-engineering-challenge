# Research and design decisions: Neon Tactical Coach

**Basis**: Repository inspection on 2026-10-06 at the accepted Hazard Arena revision `8e0aa82`. These are local design decisions, not live-model results or claims about the current provider SDK.

## Evidence provenance and snapshot size

The canonical game object lives only in `src/game.js` in the browser; the server cannot read it. The browser must derive a compact request-scoped view, and the new endpoint must validate it before any provider attempt. `get_tactical_snapshot({})` returns a fresh immutable copy of that validated view. This tool proves that the model received application-validated request evidence, not that a remote server independently observed the ball. Server checks reject impossible count/score/status combinations; a malicious client may still falsify a plausible view. This advisory-only scope does not grant game authority.

Keep: status, score, lives, bricksRemaining, normalBricksRemaining, armoredBricksRemaining, bricksByZone, armoredByZone, ballDirection, shield zone/direction and portalState. These are enough to compare opportunity and risk without raw arrays or coordinates. Brick zones use each brick's center x in arena thirds `[0, 800/3)`, `[800/3, 1600/3]`, `(1600/3, 800]`; ties to center. Shield zone uses shield center with the same boundaries. Ball horizontal and vertical direction include `neutral` for zero velocity. Counts describe *alive bricks*, including damaged armor; no per-brick HP or exact trajectory is inferred. Portal cooldown >0 maps to `cooldown`, otherwise `available`. Required `snapshotVersion: 1` is only a bounded schema version; the server rejects other versions. No extra client snapshot ID, digest or nonce is needed: one immutable snapshot belongs to one request, repeat keys live in that run, and stale provider/tool responses are checked against the active state/call. No cryptographic or server-observed game-state semantics are implied.

The Week 4 request remains four fields and is untouched. This richer state is sent only to a separate Week 5 endpoint. No hidden backend state is borrowed from Week 4.

## Smallest useful candidate

Use all four proposed categorical fields: `targetZone`, `style`, `paddleContact`, `route`. Each changes an evaluator result: target selects live targets; style changes bounded risk; paddle contact expresses the approved -240/0/+240 aiming choice; route distinguishes direct travel from the fixed portal pair. Omitting route would hide a core arena choice; omitting contact would prevent actionable paddle advice. No coordinates, timings, free-form tool arguments or arbitrary actions.

The evaluator accepts one candidate only if its target has at least one alive brick and a requested portal is currently available. It returns `candidateAccepted=false` plus fixed reason codes otherwise. An unaccepted candidate stops the run after the required evaluation; no second candidate/loop is allowed. This tradeoff keeps the three-step Core flow exact. The model sees a current snapshot before proposing, so a correct candidate can normally be chosen on the first attempt.

## Transparent deterministic evaluator

Compute `targetOpportunity = bricksByZone[targetZone]` and `armoredTargets = armoredByZone[targetZone]`. `paddleAligned = paddleContact === targetZone` is a coarse directional cue, not a predicted landing point. `shieldInTargetZone = shield.zone === targetZone` marks possible interference, not a guaranteed block. `portalAvailable = portalState === available`; `routeUsable` is true for direct or for portal when available. The fixed portal pair links left and right lanes; a portal route targeting center is rejected because the route does not directly serve a center target. This is a tactical heuristic, not exact physics. `riskLevel` uses an explicit table: one life always high; two lives are low/medium/high for safe/balanced/aggressive; three lives are low/low/medium respectively. The evaluator does not recommend replacement style/contact fields; these cues remain facts about the submitted candidate. Evidence codes are deterministic: `target_count`, `armored_count`, `lives`, `paddle_alignment`, `shield_zone`, `portal_state`, `risk_rule`. No fake percentage or long-horizon simulation.

The final response must repeat the accepted candidate's `targetZone`, `style` (as final `strategy`), `paddleContact` and `route` exactly. Evidence is selected by fact reference from the actual snapshot/evaluation result; the application checks every reference against materialized facts and requires at least one `tactical_snapshot` and one `strategy_evaluation` reference. The UI can render fact labels and values from validated server evidence, avoiding model-authored unsupported findings. The model may improve summary/action wording within validated facts, but cannot decide orchestration success or switch candidates. Summary/actions may not claim exact future outcomes.

## Bounded orchestration

One **model step** is one required successful logical output: snapshot proposal, evaluation proposal, final plan. One **provider attempt** is a single call to the server-selected model and may be retried once globally for retryable transient failure. One **tool call** is one validated local invocation. Choose `MAX_AGENT_STEPS=3`, `MAX_TOOL_CALLS=2`, `MAX_PROVIDER_CALLS=4`, `MAX_GOAL_CODE_POINTS=240`, `MAX_TOOL_RESULT_BYTES=8192`, `PER_CALL_TIMEOUT_MS=5000` and `TOTAL_AGENT_DEADLINE_MS=22000`. Normal success uses 3 steps/3 attempts/2 tools; one transient retry uses 3 steps/4 attempts/2 tools. A retry is not a step. Four 5 s attempts leave 2 s for at most one ≤250 ms backoff, validation and local tools. The absolute deadline bounds all of them; each attempt timeout is `min(PER_CALL_TIMEOUT_MS, remaining global deadline)`. One retry globally, only for timeout/unavailable/rate-limited and only if time remains. Tool work is synchronous, constant-time over a fixed-size snapshot; check elapsed time against a 100 ms local tool budget after execution. No general-purpose evaluator or unbounded loops. Provider attempts never advance the logical step; a successful step alone does.

The primary loop control is the fixed `NEED_SNAPSHOT → NEED_EVALUATION → NEED_FINAL` state machine; each state accepts only its one prescribed output. It does not continue after a rejected candidate. Defense-in-depth repeat key: `state + validated tool name + canonical validated arguments`, stored only for this run and recorded before execution. The run itself supplies request/snapshot identity; no extra ID or digest is necessary. Repeated names/keys and out-of-order proposals stop. The next state transition is allowed only after validating the matching tool result. Final validation requires both evidence objects and accepted evaluation.

## Provider and evidence policy

Use a dedicated Week 5 `createTacticalCoachGeminiProvider` (or equivalent) behind a provider-neutral interface; leave the Week 4 endpoint, orchestrator and Gemini provider behavior unchanged. The Week 4 provider accepts `toolDeclarations`/`toolResults` parameters but does not send them to Gemini and is specialized for the `{hint,category}` final response. The new adapter must send function declarations, parse one tool proposal, return validated tool results as model context, handle the structured final plan and normalize either outcome for the W5 orchestrator. The existing server-selected `gemini-3.5-flash-lite` and `@google/genai` stack are intended to support function calling and structured output, consistent with [Google's model capability page](https://ai.google.dev/gemini-api/docs/models/gemini-3.5-flash-lite) and [GenAI SDK function-calling guide](https://googleapis.github.io/js-genai/release_docs/index.html). This is a design expectation, not proof of the exact three-step integration: confirm pinned SDK/model behavior and reliability in a limited live phase. No provider/model choice comes from browser input. No live call, pricing claim or secret use occurs in this design task.

The new `specs/003-neon-tactical-coach/` artifacts are the source of design truth. During implementation, dedicated `docs/AGENT_EVALS.md` and `docs/EVIDENCE_W05.md` can record observed fixture/live/manual results, while `docs/AI_USAGE_LOG.md` gets dated pair-work entries. Avoid duplicating contracts in `docs/`; link the structured contracts here. Preserve Week 3, Week 4 and Hazard Arena history.

## Open implementation checks

- Confirm the chosen server-controlled model/SDK can produce the required two tool proposals and final structured output in the pinned environment. If not, select and document a different server-controlled adapter/model before live use; no browser selection or silent fallback.
- The current local Node API has no known application request boundary shorter than 22 s; `server/ai/contracts.ts` permits provider request `timeoutMs` up to 30 s. Actual deployment/proxy timeout is unverified. Confirm it during live integration, and keep the Coach's total deadline below the outer deployed HTTP request boundary (tighten the budget if needed).
